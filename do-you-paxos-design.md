# Do You Paxos? — Design Document

A static web app (GitHub Pages, TypeScript) that teaches and tests consensus protocols by asking learners to judge small concrete scenarios: steps, states, and traces. It is an inverted version of the PICK workflow from Prasad, Austen, Fisler, Krishnamurthi, "Meaningful Human-in-the-Loop Checking of GenAI Synthesis for Restricted Languages" (ECOOP 2026, https://www.siddharthaprasad.com/papers/pafk-pick.pdf).

This document is the spec for the implementing agent. Read it fully before writing code. Where it says TODO(Murat), leave a clearly marked placeholder and do not invent content.

---

## 1. Background: PICK, inverted

PICK has several candidate formal artifacts and an unknown user intent. It shows the user concrete scenarios drawn from where the candidates disagree, the user labels each scenario, and candidates inconsistent with the labels are eliminated.

Here the roles flip:

- The **correct protocol** is known (the ground truth).
- The **candidates** are the correct protocol plus **mutants**, each encoding one known misconception (for example, "phase 2 may propose any reported value, not the one with the highest ballot").
- The **unknown** is the learner's mental model.
- Each question is built from scenarios on which the correct protocol and one or more mutants **disagree**. The learner's answers reveal which misconceptions they hold.

Scenarios that every candidate agrees on teach nothing and are never shown.

### 1.1 Two departures from PICK, and why

**(a) Forced choice instead of accept/reject.** PICK asks the user to accept or reject one scenario at a time. That does not survive the inversion. Mutants P1–P7 all *add* behaviors to Paxos, so every scenario they distinguish has correct answer "not allowed." A learner who answers "no" to everything would score perfectly and be diagnosed as holding no misconceptions. PICK does not have this problem because its candidate languages genuinely overlap in both directions; ours are mostly supersets of the truth.

So the atomic unit of interaction here is a **pair**, judged together with one 4-way answer (§6.1). The bank enforces a mix of pairs where exactly one member is legal, where both are, and where neither is, so no constant answer beats chance.

**(b) Pairs share a contrast feature by construction.** The PICK paper notes (§6, "The value of contrasting examples") that its pairs "are not fully aligned with contrasting case theory in that there is no guarantee that our algorithm chooses two scenarios that differ in a common underlying feature." Here we can guarantee it: the partner scenario is generated by perturbing **exactly one parameter of the same action** from the same pre-state. The learner sees two nearly identical pictures and has to find the one feature that matters. That is what contrasting-case theory actually asks for.

### 1.2 Why steps, not states, are the backbone

PICK requires (its §2.3) that scenarios be "small, self-contained, and not requiring extensive cross-referencing to evaluate." The paper's §7.1 explains why they skipped SQL: a query is meaningful only relative to a database, so the object the human must judge is a *pair*, and judgment means cross-referencing rather than a localized call.

A Paxos **state** has exactly the SQL shape. Judging "can Paxos reach this state?" means reconstructing a plausible history from a message set — unbounded backward reasoning whose cost grows with the bounds. A Paxos **step** is the regex-like object: self-contained, locally decidable against one guard, fixed judgment cost regardless of how big the state space is.

Therefore: **steps are levels 1–2 and the backbone of the diagnosis. States are demoted to level 6 and admitted only when a short justification exists (§6.6).** Traces are a presentation format, not an independent source of discrimination (§6.5).

## 2. Goals and non-goals

### Goals

1. Teach the rules and invariants of single-decree Paxos to someone learning it, and separately test someone who believes they already know it.
2. Diagnose specific misconceptions, not just give a score.
3. Extend to Raft, then to a Paxos-vs-Raft comparison level, then to variants (Flexible Paxos first).
4. Zero running cost: static site on GitHub Pages, no backend, no LLM calls at runtime, no accounts.
5. Every answer the app treats as correct must be backed by model checking, and the JavaScript models must be cross-checked against reference TLA+ specs with TLC in CI.
6. Every question must carry a machine-generated justification that references only facts visible in the rendering (§10.5). A question whose answer cannot be explained is not shipped.

### Non-goals (v1)

- No in-browser TLA+ parsing or TLC.
- No user-authored specs.
- No server-side analytics or result collection. Progress lives in `localStorage` only.
- No liveness questions in v1 (safety only). Liveness and lasso traces are a later milestone.
- **No research-instrument mode.** Running this as a PICK-style controlled study would need persisted participant state, consent flow, and condition assignment — all of which need a backend. TODO(Murat): revisit if and when the app ships successfully and is worth studying.

## 3. Architecture overview

```
TLA+ reference specs ──(TLC in CI)──┐
                                     ├── cross-check: same reachable sets, same traces
TypeScript models ──(Node BFS)───────┘
        │
        ▼
Bank generator (Node, build time)
        │   computes reachable state graphs for correct + each mutant,
        │   step-difference sets, membership vectors, contrast pairs,
        │   justifications, bound-stability filtering
        ▼
Question banks (static JSON, committed to repo)
        │
        ├──► Verification harness (synthetic learners, §10.6)
        ▼
Web app (Vite + React + TypeScript), deployed to GitHub Pages
        │   adaptive pair selection, rendering, diagnosis
        ▼
Learner
```

Key decision: **all model checking happens at build time**. The browser only loads precomputed question banks with membership vectors and runs the selection and scoring logic. This keeps the app fast, keeps Pages free, and means correctness depends only on the build pipeline, which CI verifies.

## 5. Models

### 5.1 Model interface

Each protocol is a TypeScript module parameterized by constants (bounds) and mutation flags. The state shape must mirror the TLA+ variables one-to-one so states can be serialized to TLA+ for cross-checking.

**Guards are structured, not opaque booleans.** This is load-bearing: it is what makes justification generation (§10.5) free, and what makes a mutation flag a precise edit to a named conjunct rather than a rewrite of an action.

```ts
type Value = string | number | boolean | null | Value[] | { [k: string]: Value };

interface Conjunct<S> {
  id: string;                   // e.g. "phase2b.ballotAtLeastPromised"
  holds(s: S, params: Params): boolean;
  // structured references to the state fields this conjunct reads,
  // used to check that the rendering shows what the learner needs (§10.5)
  reads(s: S, params: Params): FieldRef[];
}

interface Action<S> {
  name: string;                 // e.g. "Phase2b"
  domain(s: S): Params[];       // all candidate parameter bindings, enabled or not
  guard: Conjunct<S>[];         // ORDERED; evaluated in order
  effect(s: S, params: Params): S;
  sends(s: S, params: Params): Value[];
  reads(s: S, params: Params): Value[];   // messages consumed/read, for space-time diagrams
}

type Enabled =
  | { ok: true }
  | { ok: false; failed: string };        // id of the FIRST false conjunct

interface Model<S> {
  id: string;                   // "paxos"
  title: string;
  constants: Record<string, Value>;
  flags: Record<string, boolean>;          // mutation flags, all false = correct protocol
  init(): S[];
  actions: Action<S>[];
  enabled(s: S, a: string, params: Params): Enabled;
  successors(s: S): ActionInstance<S>[];   // all enabled action instances
  predicates: Record<string, (s: S) => boolean>; // invariants, "chosen" definitions, etc.
  symmetry?: Symmetry<S>;                  // permutations of acceptor ids, values
  toTLA(s: S): string;                     // serialize to TLA+ value syntax
  view: ViewSpec;                          // how the web app renders a state (§8)
}

interface ActionInstance<S> {
  action: string;
  params: Params;
  reads?: Value[];
  sends?: Value[];
  next: S;
}

type ModelFactory<S> = (constants: Record<string, Value>, flags: Record<string, boolean>) => Model<S>;
```

Rules:

- States are plain immutable JSON-compatible objects. Sets are represented as arrays and **must be canonicalized** (sorted by canonical serialization) before hashing or comparison.
- `canonicalKey(s)` = stable JSON with sorted object keys and sorted set arrays.
- Symmetry reduction: `symmetricKey(s)` = the lexicographically smallest `canonicalKey` over all permutations of symmetric model values (acceptors, values). With 3 acceptors and 2 values that is 12 permutations, which is cheap. Use symmetry for deduplicating questions, **never for what gets rendered** — the learner is always shown a concrete representative with real acceptor names, and never the canonical form.
- A mutation flag must be expressible as exactly one of: drop conjunct `X`, replace conjunct `X` with `X'`, or replace `effect` with `effect'`. If a mutant cannot be expressed this way, it is too coarse; split it.
- Action instances must record which message they read (`reads`), so traces can be drawn as space-time diagrams.

### 5.2 Paxos model (single-decree)

Base the model on Lamport's `Paxos.tla` from the TLA+ Examples repository (check its license and attribute it). Variables:

- `maxBal[a]`: highest ballot acceptor `a` has promised (init −1)
- `maxVBal[a]`, `maxVal[a]`: ballot and value of `a`'s last vote (init −1, None)
- `msgs`: set of all messages ever sent (monotonic; messages are never removed)

Actions and their named conjuncts (use Lamport's guards exactly in the correct configuration):

| Action | Conjunct id | Meaning |
|--------|-------------|---------|
| `Phase1a(b)` | — | always enabled for `b` in the ballot bound |
| `Phase1b(a)` | `phase1b.newer` | a 1a message exists with `m.bal > maxBal[a]` |
| `Phase2a(b,v)` | `phase2a.noPriorProposal` | no 2a message for ballot `b` yet |
| | `phase2a.quorumPromised` | 1b messages for `b` from a quorum `Q` |
| | `phase2a.highestReported` | if any member of `Q` reports a vote, `v` is the value reported with the highest `mbal` |
| `Phase2b(a)` | `phase2b.ballotAtLeastPromised` | a 2a message exists with `m.bal >= maxBal[a]` |

Effects: `Phase1b` raises `maxBal[a]` to `m.bal` and reports `(maxVBal[a], maxVal[a])`; `Phase2b` sets `maxBal[a]`, `maxVBal[a] := m.bal` and `maxVal[a] := m.val`.

Derived predicate `Chosen(v)`: there exist a ballot `b` and a quorum `Q` such that every acceptor in `Q` sent a 2b message for `(b, v)`.

Default bounds (the agent must measure state counts and adjust; report counts in the README):

- Acceptors: 3, quorums: majorities
- Values: 2
- Ballots: `{0, 1}` as default; `{0, 1, 2}` for mutants that need three ballots to show a difference (§5.5)

Target: each configuration under about 500k distinct states without symmetry, so the bank build finishes in minutes in CI. The bound-stability filter (§6.4) needs BFS at bound `k+1` as well, so budget for roughly double. If a configuration is too large, reduce bounds rather than adding cleverness.

### 5.3 Paxos mutants

Each mutant flips exactly one flag. Mutants share all variables and actions with the correct model, so differences are directly comparable at the step level.

Mutants come in three kinds, and the third was a surprise. **Adding mutants** enlarge the transition relation; **restricting mutants** shrink it; **overlapping mutants** do both. P5 and P6 edit what `Phase1b` *does* rather than when it fires, so they reach states Paxos cannot and fail to reach states Paxos can — measured at two ballots, P5 gains 3,496 states and loses 2,088.

We need the non-adding kinds: they are the only source of pairs where the correct answer is "yes, Paxos allows both" (§6.3), and without enough of them the answer key is all-no and a constant answer beats the game. P9–P11 were added for that reason; the overlapping mutants supply it for free.

**The direction column is measured, not asserted.** `packages/engine/src/engine.test.ts` derives it from the reachable sets and fails if this table drifts. That check is what found P5 and P6 to be overlapping rather than adding, as originally specified here.

| ID | Flag | Change | Misconception it encodes |
|----|------|--------|--------------------------|
| P1 | `ownValue` | drop `phase2a.highestReported` | "The leader proposes its own value." |
| P2 | `anyReported` | weaken `phase2a.highestReported` to "any reported value" | "Any previously accepted value is safe to re-propose." |
| P3 | `noQuorumPhase1` | weaken `phase2a.quorumPromised` to one acceptor | "One promise is enough to start phase 2." |
| P4 | `ignorePromise` | drop `phase2b.ballotAtLeastPromised` | "Acceptors accept whatever they are sent." |
| P5 | `forgetfulPromise` | `Phase1b` effect reports no prior vote (`mbal = -1`) — *overlapping* | "A promise is just an ack; it does not carry history." |
| P6 | `noPromiseUpdate` | `Phase1b` effect does not raise `maxBal[a]` — *overlapping* | "Promising does not constrain future accepts." |
| P7 | `multiProposalPerBallot` | drop `phase2a.noPriorProposal` | "Two proposals can share a ballot." |
| P8 | `strictAccept` | `phase2b.ballotAtLeastPromised` becomes strict (`>`) | "An acceptor cannot accept the ballot it promised." |
| P9 | `unanimousPhase1` | `phase2a.quorumPromised` requires all acceptors | "Phase 1 needs everyone, not a majority." |
| P10 | `voteOnce` | new conjunct: `maxVBal[a] = -1` | "An acceptor votes at most once, ever." |
| P11 | `monotoneBallots` | new conjunct on `Phase1a`: `b` must be the smallest unused ballot | "Ballots must be used in order, with no gaps." |

Explanations for each misconception go in `content/paxos/misconceptions.yaml`: id, title, one-line statement of the misconception, the correct rule, why it matters. Rule text for each named conjunct goes in `content/paxos/rules.yaml` and is what the justification generator (§10.5) splices in. TODO(Murat): review all explanation text. The agent may draft text but must mark it `status: draft`.

### 5.4 "Chosen" definition candidates (predicate-only, no new BFS)

Some misconceptions are about definitions, not rules. These are predicates evaluated on states of the correct model:

| ID | Predicate | Misconception |
|----|-----------|---------------|
| C0 | Correct `Chosen(v)` (quorum of 2b in the same ballot) | — |
| D1 | Majority sent 2b for `v`, possibly in different ballots | "Chosen = a majority accepted v at some point." |
| D2 | Some 2a for `v` exists | "Chosen = proposed." |
| D3 | Some acceptor sent 2b for `v` | "Chosen = accepted by anyone." |
| D4 | A majority currently has `maxVal = v` | "Chosen = a majority currently holds v." |

D1 vs C0 is the most important one. It is also the classic trap behind "the value with the highest ballot among a majority" reasoning.

**D1 and D4 are equivalent and must be collapsed.** They agree on every reachable Paxos state — verified over 34,913 of them. This is not an artifact of the bound; it is the safety theorem showing through. For a majority that voted for `v` to stop *holding* `v`, some acceptor in it would have to vote for something else later, and any quorum promising a later ballot intersects that majority and is forced to re-propose `v`. So no question can ever separate them, and shipping both would mean naming a misconception the learner may not hold. The generator detects the equivalence over the reachable set and merges them into one candidate, which is PICK's own "collapse equivalent candidates" step (paper §2.3).

Note also that the definitions form a **containment chain**: `D1+D4 ⊂ D3 ⊂ D2`. Every state that is evidence for a stricter definition is equally evidence for every looser one. That has consequences for scoring — see §7.2.

These are the cheapest questions in the whole design: both directions of disagreement occur naturally, so no answer-mix engineering is needed. They are level 3.

### 5.5 Mutants that need larger bounds

Some mutants are indistinguishable from the correct protocol at small bounds. Example: P2 needs at least three ballots, because with ballots `{0, 1}` the 1b messages seen in ballot 1 can only report votes from ballot 0, and ballot 0 has at most one value.

The bank generator must:

1. Compute the **step**-difference set for each mutant at the default bounds.
2. If it is empty, retry at the next larger bound configuration listed for that mutant.
3. If it is still empty, report the mutant as "equivalent at all tested bounds," exclude it from banks, and fail CI loudly so a human looks at it.

**Equivalence is per question kind.** A mutant can have `R_i = R_C` (nothing to say at the state level) while `T_i ≠ T_C` (plenty to say at the step level) — the mutant reaches the same places by illegal routes. The generator reports a per-kind equivalence table; only *step*-level equivalence at all tested bounds is a CI failure.

### 5.6 Raft model (later milestone)

A reduced Raft with **atomic RPCs** (request and response handled in one step) to keep the state space small. This is a deliberate coarsening; note it in the level intro. Message-level Raft is out of scope.

- Servers: 3. Terms: up to 3 (measure; Figure-8-style bugs may need 4). Log length: up to 2. Values: 2.
- Variables: `currentTerm[i]`, `votedFor[i]`, `role[i]`, `log[i]` (sequence of `[term, value]`), `commitIndex[i]`.
- Actions: `Timeout(i)`, `RequestVote(i, j)` (atomic grant/deny), `BecomeLeader(i)`, `ClientRequest(i, v)`, `AppendEntries(i, j)` (atomic, with consistency check and conflict truncation), `AdvanceCommitIndex(i)`.

Raft mutants:

| ID | Change | Misconception |
|----|--------|---------------|
| R1 | Leader advances commit for an entry from an older term by counting replicas | Figure 8 of the Raft paper |
| R2 | Vote granted without the log up-to-date check | "Any candidate with the highest term can win." |
| R3 | A server may vote twice in one term | "Votes are per request, not per term." |
| R4 | Follower appends without the prevLogIndex/prevLogTerm check | "Followers just append what the leader sends." |
| R5 | Leader may overwrite its own log entries | "The leader's log is mutable like followers'." |

Raft needs restricting mutants too, for the same answer-balance reason. TODO(Murat): propose 2–3.

## 6. Question generation (build time)

### 6.1 The question form

**A question is a pair of scenarios of the same kind, presented side by side, answered with one 5-way choice:**

> **A only** · **B only** · **Both** · **Neither** · **Unsure**

A and B differ in exactly one feature (§6.2). "Unsure" marks the question seen without affecting scores, as in PICK.

This is mechanically two membership judgments delivered as one contrastive decision. It keeps PICK's accounting — every answer is a statement about every candidate — while making a constant answering strategy useless.

**Pair types and what each is for.** Let `μ(x)[j]` be the membership of scenario `x` under config `j`. The pair's type is given by `(μ(A)[C], μ(B)[C])`:

| Type | Truth | Diagnostic job | Target share |
|------|-------|----------------|--------------|
| `one` | exactly one is legal | separates an *adding* mutant from correct | 60% |
| `both` | both are legal | separates a *restricting* mutant from correct | 20% |
| `neither` | neither is legal | separates adding mutant `i` from adding mutant `j` | 20% |

The `neither` type is the one that earns its keep. Misconceptions are correlated — a learner who believes the leader proposes its own value (P1) will answer like P3 and P5 on most `one` pairs. A `neither` pair, where Paxos forbids both members but mutant `i` allows A and mutant `j` allows B, is the only thing that pulls them apart. See §10.6.

Shares are targets enforced at bank build, not hard quotas; the generator reports the achieved mix and CI fails if any type falls below half its target.

### 6.2 Generating the pairs

Everything derives from one primitive: **step difference**. Do not compute trace difference or state difference independently (§6.5, §6.6).

For a protocol with correct config `C` and mutants `M1..Mk`:

1. **BFS** each config. Produce the reachable set `R_j` (keyed by `canonicalKey`) and the transition relation with action instances. Do this at bound `k` and bound `k+1` (§6.4).

2. **Enumerate candidate steps.** For each `s ∈ R_C` and each action `a` and each `params ∈ a.domain(s)`, form the step `x = (s, a, params, effect(s, params))`. Note this enumerates steps that *no* config allows as well — those are useful as filler in `neither` pairs.

3. **Membership vector.** `μ(x)[j] = (enabled_j(s, a, params).ok)`, for every config `j`, including `C`. As in PICK, one answer informs every candidate.

4. **Perturbation neighborhood.** `N(x)` = steps `y` from the same pre-state `s` such that `x` and `y` differ in exactly one of:
   - one parameter of the same action (distance 1, strongly preferred),
   - the message read by the same action (distance 1),
   - the action name, with all else comparable (distance 2, fallback).

   A pair with distance > 2 is not a contrasting case and must not be shipped.

5. **Admissibility.** `(x, y)` with `y ∈ N(x)` is admissible iff the joint vector `(μ(x), μ(y))` differs between at least two configs — *not necessarily including `C`*. This generalizes PICK's Algorithm 1 step 2 (which ranges over all pairs `{f_i, f_j} ⊆ R`) and is what admits the `neither` type.

6. **Scoring.** Rank admissible pairs by, in order: number of config pairs separated; pair type fills an under-filled quota; smallness of `s` (message count); distance 1 over 2; distinct `symmetricKey` from already-selected pairs. Take up to `K = 20` per mutant per level.

7. **Justify.** Generate a justification for each member (§10.5). A pair where either member cannot be justified is dropped, not fixed.

8. **Seeded RNG for all choices.** The same inputs must produce byte-identical banks.

### 6.3 Where `both` pairs come from

A `both` pair needs two steps Paxos allows and some mutant forbids. That mutant must be restricting, which is why P8–P11 exist. Concretely: `Phase2b(a)` where `m.bal = maxBal[a]` exactly is legal in Paxos and forbidden by P8; `Phase2a` with a bare majority is legal and forbidden by P9; a second vote by an acceptor is legal and forbidden by P10.

If the restricting mutants do not supply enough `both` pairs to hit the 20% target, add more restricting mutants rather than relaxing the target. Do not pad with same-answer pairs that separate nothing.

### 6.4 Bound-stability filtering

Some answers depend on the bounds rather than on Paxos. The clearest case: "can value `v` still be chosen from here?" is partly a question about whether any ballots remain. With ballots `{0,1}`, once ballot 1 is used the answer is "nothing more can be chosen" — an artifact of the bound. **TLC will confirm this answer, because the TLA+ spec has the same bound.** Cross-checking catches implementation divergence, not semantic artifacts.

Therefore, for any question whose answer is a reachability-closure property (`future`, `locked`, and the `chosen` questions that quantify over successors):

1. Compute the answer on the bound-`k` graph and on the bound-`k+1` graph.
2. Ship only questions whose answer is identical under both.
3. Additionally cross-check against an **independent oracle** (§10.4) derived from the safety argument rather than from the graph.
4. Report the drop rate. If filtering removes more than half the candidate questions, the bound is too tight; raise it rather than shipping the survivors.

Step questions are local and need no stability filter. State-reachability questions do: a state unreachable at bound `k` may be reachable at `k+1`. Apply the filter there too.

### 6.5 Traces: locate the first illegal step

For models that share `Init` and variables, a behavior is legal exactly when every one of its steps is legal. So **trace questions carry no discriminating information beyond step questions**, and asking "could this execution happen?" as a yes/no is a wasted question — it is a conjunction of step judgments collapsed into one bit.

Instead, the trace question is:

> Here is an execution that ends badly (two different values chosen). **Click the first step that Paxos does not allow.**

The answer is mechanically derived: the least index `t` with `(s_t, s_{t+1}) ∉ T_C`. It is localized, the distractors are the other steps, and a wrong click identifies the misconception directly — clicking later than `t` means the learner accepted the illegal step, and *which* conjunct it violates names the misconception.

Generate these from the shortest behavior in each safety-breaking mutant that reaches a state with two chosen values. Keep them short: target at most 8 steps, hard limit 12.

### 6.6 States: only with a short justification

State reachability is the hardest judgment in the game (§1.2) and goes last. Admit a state question only if one of these holds:

- **Reachable with a short witness:** `s ∈ R_C` with a shortest path from an initial state of length ≤ 3. The justification is the witness path.
- **Unreachable for a local reason:** `s ∉ R_C` and `s` violates a named invariant that the learner has already been taught at an earlier level. The justification is that invariant.

A state that is unreachable only because BFS says so gets no justification and is not shipped. "The model checker says no" is not an explanation, and level 6 is in the Learn track where explanations are the point.

Pairs at this level perturb one field of the state (one acceptor's `maxBal`, one message's value).

### 6.7 Comparison level (Paxos vs Raft)

The two protocols have different variables and action granularity. Compare them only through an abstraction function (refinement mapping) onto a shared observable view, ignoring internal steps (stuttering). Do not compare raw traces.

- Use Multi-Paxos with 2 slots for this level, not single-decree Paxos. This needs a third model, `multipaxos`, with phase 1 covering all slots.
- Abstract view per node: `term` (Paxos ballot / Raft term), `entries[slot]` = `(term, value)` or empty, and `committed[slot]`.
- An abstract scenario belongs to protocol `P` if some reachable concrete state of `P` maps to it. Compute this by mapping all reachable states of each protocol and taking the image sets.
- Good question sources are where the images differ:
  - **Gaps:** Paxos allows slot 2 accepted while slot 1 is empty; Raft does not.
  - **Re-proposing old values:** Paxos re-proposes an old value under a new ballot, while Raft keeps the original term on an entry.
  - **Election restriction:** Raft's up-to-date log check versus Paxos phase 1 adopting values.

  See Howard and Mortier, "Paxos vs Raft: Have we reached consensus on distributed consensus?" (PaPoC 2020).
- Answers: "Paxos only," "Raft only," "both," "neither" — the only level where the 4-way answer is about protocols rather than about pair membership.

**The abstraction function is hand-written and must be checked.** `α` is the one piece of this level with no oracle behind it, and a bug in it silently produces wrong answers for every question. Obligation: every concrete step must induce an abstract step or a stutter. This is a standard TLC refinement check and must be in CI before this level ships.

### 6.8 Bank schema

```ts
interface Bank {
  protocol: "paxos" | "raft" | "compare";
  level: string;                  // e.g. "paxos-phase2-steps"
  generatedFrom: { modelVersion: string; constants: object; flags: string[]; seed: number };
  configs: string[];              // ["correct", "P1", ..., "P11"]
  questions: Question[];
  mix: { one: number; both: number; neither: number };   // achieved shares
}

interface Question {
  id: string;
  kind: "step" | "chosen" | "future" | "trace-locate" | "state" | "which";
  type: "one" | "both" | "neither";   // for pair kinds
  a: Scenario;
  b: Scenario;                        // absent only for trace-locate
  distance: 1 | 2;
  answer: Record<string, AnswerValue>;  // per config: pair membership, value set, or index
  targets: string[];                    // config pairs this question separates
  size: number;                         // messages or steps, for difficulty ordering
  boundStable?: boolean;                // present and true for closure-property kinds
}

interface Scenario {
  payload: StatePayload | StepPayload | TracePayload;  // render-ready
  justification: Justification;         // §10.5
}

interface Justification {
  verdict: "legal" | "illegal";
  conjunct?: string;                    // id of the first failing conjunct, if illegal
  refs: FieldRef[];                     // state fields the reasoning depends on
  text: string;                         // assembled from content/paxos/rules.yaml
}
```

Payloads include the action instance metadata (`action`, `params`, `reads`, `sends`) so the web app can draw arrows and highlight diffs without knowing protocol semantics.

## 7. Tracks, selection, and diagnosis (runtime)

### 7.1 One mode, always with feedback

The original design had a Learn track and a Test track, the latter withholding feedback until the end so that answers would not be shaped by earlier ones. **That was dropped after the first play-through.** Withholding feedback is the right call for a measurement instrument; it is the wrong call for the thing this actually is, which is a teaching tool. Someone who has just worked out a hard judgement wants to know immediately whether they were right, and a diagnosis delivered fourteen questions later arrives too late to attach to anything they remember thinking.

So: **one mode, immediate feedback after every question**, showing the verdict for each option, the rule each turns on, and — when the answer matches a mutant — that misconception's explanation. The end-of-level diagnosis still runs; it is a summary, not the payoff.

**What ships is single-decree Paxos and nothing else** — three levels, one mode. Raft and the protocol-comparison level (§6.7) stay in this document as later milestones rather than appearing in the product as a placeholder: a menu entry for something that does not exist is a promise the app cannot keep, and it makes the thing that does work look unfinished. The candidate list is never shown; showing it would give the answers away.

### 7.2 Learner model

PICK keeps one set of candidates and eliminates them with a two-downvote threshold, a deliberately robust scheme for noisy users. We track each misconception independently instead, because a learner can hold several at once.

- For each misconception `i`: `p_i` = probability the learner holds it. Prior 0.3.
- Answer noise: `ε = 0.1` (a learner without misconception `i` still answers wrong with probability ε; configurable).
- A 5-way answer decomposes into two membership judgments, one for A and one for B. The likelihood of the observed answer under the hypothesis "the learner follows config `j`" is the product over `{A, B}` of `(1 − ε)` where the judgment matches `μ(·)[j]` and `ε` where it does not. Update `p_i` by Bayes against config `C`.
  - If `μ(A)[i] = μ(A)[C]` and `μ(B)[i] = μ(B)[C]`, this question says nothing about `i`; no update.
  - "Unsure" means no update. Record it.
- Answers can be changed later from the history drawer, as in PICK. **Recompute all `p_i` from scratch from the full answer history.** Never update incrementally only.

**The independence assumption is known to be wrong**, and the design does not pretend otherwise. Misconceptions are correlated: a learner holding P1 answers like P3 and P5 on most `one` pairs. The consequence is that the posterior can confidently report three misconceptions where the learner holds one. Three defenses:

1. `neither` pairs (§6.1) are specifically generated to separate adding mutants from each other. Selection scores coverage of **config pairs**, not just of individual mutants — separating a mutant from Paxos is not enough if every question that does so separates its neighbour identically. Adding this alone took the P5/P6 cross-flagging rate from 90% to 24% and the P8/P10 rate from 90% to 9%.
2. **Exclusive candidate sets get a categorical posterior, not independent ones.** This is a correction to the original spec, which applied independent per-candidate Bayes everywhere. Rule misconceptions genuinely are independent — you can believe both that the leader proposes its own value and that a promise is a bare ack. **Definitions are not**: you hold exactly one definition of "chosen". Scored independently over a containment chain (§5.4), every candidate gets pushed over the threshold whichever one the learner holds, and the level reports all three every time. A bank sets `exclusive: true` and is then scored with `recomputeCategorical` and selected with `selectNextExclusive`, which is PICK's own rule — draw the next scenario from where the two leading candidates disagree. Measured effect on the `chosen` level: off-diagonal confusion fell from ~85% to ≤2%.
3. The results screen reports a misconception as "Likely" only if the bank-level separability check (§10.6) found it separable from the others at the configured ε. Misconceptions that fail that check are reported as a **cluster** — "you hold at least one of P1/P2" — rather than individually. This is honest and it is still useful.

**Where this still bites.** P1 ⊃ P2 in behaviour: every step P2 permits, P1 permits. Evidence for P2 is therefore evidence for P1, and the two cannot be fully separated by any question. The harness measures the residual confusion (P1-believers flag P2 93% of the time) and the UI reports the cluster. A categorical treatment is not available here, because unlike definitions these two *could* genuinely both be held.

### 7.3 Selection

1. Pick the misconception with the highest uncertainty (`p_i` closest to 0.5) that still has unused questions in this level.
2. Among questions targeting it, prefer: an under-represented pair type, then distance 1, then smaller `size`.
3. Present the pair side by side with the 5-way answer.
4. Stop the level when every misconception has `p_i < 0.1` or `p_i > 0.9`, or after 12 questions.

### 7.4 Results screen

For each misconception (or cluster, per §7.2), show one of:
- "Not detected" (`p_i < 0.1`)
- "Likely" (`p_i > 0.9`)
- "Unclear" (otherwise)

For "Likely" ones, show the explanation, **the specific question where the learner's answer diverged from Paxos most informatively**, and a button to practice that misconception in the Learn track. Showing the receipt matters more than showing the probability: the payoff of the whole app is being told, accurately and with evidence, what you believed without realizing it.

Offer export of the full answer history as JSON.

## 8. Rendering

The app must render protocol state for people who do not read TLA+. The rendering is driven by each model's `ViewSpec`, but v1 can hardcode renderers per protocol if that is simpler. **Correctness of the rendering matters as much as correctness of the model**, and §10.5 makes part of that a checked obligation.

**The house rule, learned the hard way: no protocol notation reaches the reader.** The first build shipped `b=1`, `v=x`, chips labelled `1a / 1b / 2a / 2b`, and acceptor names like `a2`, and it was unreadable — a reader could not tell whether `v` meant "value" or "vote", nor whether a proposer was a separate thing from the acceptors, nor whether ballot 2 was a second decision. Every §10.5 check passed on that build, because those checks ask whether the information is *present*. Present is not legible.

Concretely:

- **Every message is a full English sentence** naming who did what: "Acceptor 2 promises this ballot, and reports its last vote: Bob in ballot 1."
- **The history is grouped by ballot, not by message type.** A ballot is one attempt at the single decision, so grouping by it turns four unordered buckets into the story of each attempt, in order.
- **Values are named** (Alice, Bob) rather than `x` and `y`, which makes "has Alice been chosen?" a sentence and makes it obvious the two compete for one slot.
- **The framing is stated on screen, not assumed**: three acceptors, one decision, ballots are retries, proposers are separate from acceptors, and what "chosen" means. A reader who does not know these cannot judge anything, and nothing else in the design was telling them.
- **A step is shown as what it changes, in causal order** — what it looks at, then what it records, then what it announces — not as a second full copy of a state the reader is already looking at.
- **Cards are not clickable.** There are four possible answers and a card is half of one; letting a click stand for "only this one" silently commits an answer the reader did not choose.
- `checkNoNotation()` in the pipeline fails the build on `ballot b`, `value v`, `phase-2a`, message codes and TLA+ variable names in any reader-facing string. It caught four leaks the moment it was switched on.

### 8.1 Paxos state

- **Acceptor table:** one row per acceptor; columns `promised (maxBal)`, `voted ballot (maxVBal)`, `voted value (maxVal)`. Show −1/None as "—".
- **Message panel:** grouped by type (1a, 1b, 2a, 2b). Each message is a compact chip, for example `2b  a2  b=1  v=x`.
- **Derived facts** (for example, "chosen: x") are hidden by default. They are what the learner is supposed to work out. Learn-track feedback may show them after the answer.

### 8.2 Step pairs

The pair is the unit, so the layout is: shared pre-state once at the top, then the two candidate successors side by side as A and B. This makes the single differing feature visually obvious, which is the whole point of the contrast.

- Changed table cells and newly sent messages are highlighted relative to the pre-state.
- The action name is shown in plain words, for example "Acceptor a2 accepts the ballot-1 proposal."
- The message the action read is outlined.
- A diff toggle highlights A-versus-B, as in PICK's diff mode.

### 8.3 Traces as space-time diagrams

- One vertical lane per process. For Paxos: one lane per ballot leader, plus one per acceptor. For Raft: one per server.
- Events are dots on lanes. A message arrow goes from the sending event to the event that read it (from `reads` and `sends` metadata).
- Draw the diagram as a partial order: independent events are not given a total order visually. The learner should not read meaning into the order of unrelated events.
- For `trace-locate` questions, steps are clickable targets; clicking an event shows the state after it in the table view.
- Render with plain SVG generated in React. No diagram library is required.

### 8.4 Visual requirements

- Use a colorblind-safe palette. The PICK paper used Patrignani's syntax-highlighting recommendations; follow that spirit.
- Support light and dark mode.
- Keyboard shortcuts: `a` / `b` / `o` (both) / `n` (neither) / `u` (unsure), `Enter` for the next question.
- Layout works on a phone (cards stack vertically, which weakens the contrast — warn and prefer landscape), but desktop is the primary target.

### 9.1 Invariant and CTI level

This level teaches inductive invariants.

- The candidates are invariant formulations: Lamport's inductive invariant for Paxos, plus weakened versions, each with one conjunct dropped.
- Questions:
  - "This state satisfies agreement. Is it reachable?"
  - "Can one step from this state violate agreement?"
- Scenario sources:
  - Reachable states of the correct model (answer: reachable).
  - **Perturbed states:** reachable states with one field changed so the result satisfies the weak invariant but not the strong one. These are counterexamples to induction (CTIs).
- Generating perturbed states: apply single-field edits to reachable states, keep only those that are type-correct and in exactly the right difference set, and deduplicate by symmetry. The single-field edit is also the pair's contrast feature, so this level's pairs are free.

## 10. Correctness assurance

The app is only useful if its answers are right, its questions are answerable, and its diagnosis actually diagnoses. Those are three different claims needing three different kinds of evidence.

**The TLC cross-check is a replication check**: two implementations of the same semantics agreeing. It cannot catch an error *in* the semantics, in the question selection, in the rendering, or in the diagnosis. Layers 3–5 below exist because of that.

### 10.1 Layer 0 — unit tests (vitest, `packages/engine` and `packages/models`)

- **Toy model:** BFS state count matches a hand-computed number; canonicalization is order-independent; symmetry keys collapse permuted states.
- **Selection and scoring:** Bayes updates, and full recomputation on answer edits matching incremental computation when no edit occurred.
- **Pair construction:** every generated pair has distance ≤ 2 and separates ≥ 2 configs.

### 10.2 Layer 1 — the TypeScript model is the TLA+ spec

Download a pinned `tla2tools.jar` release in CI and cache it. For each config (correct and each mutant), without symmetry:

1. **Reachable sets, not counts.** Dump TLC's state set (`-dump`) and compare it *set-wise* against the JavaScript BFS result under a shared canonical serialization. Matching cardinalities is a much weaker check for the same cost — two different models can easily agree on a count.
2. **Trace membership.** Sample 200 random JavaScript behaviors (seeded, depth at most 10). Serialize each with `toTLA` into a generated trace-validation module, and check with TLC that the sequence is a behavior of the corresponding spec. Standard pattern: a variable `i` indexes the trace, `Init` constrains state to `Trace[1]`, `Next` constrains `vars' = Trace[i+1]`. TLC reaching `i = Len(Trace)` means the trace is accepted.
3. **Answer spot checks.** For a sample of 50 bank questions per level, re-derive each answer with TLC. Reachability: assert `~(vars = s)` as an invariant; a violation means `s` is reachable. Step legality: check `Next` for a fixed `(s, s')`.
4. **The flagged spec does not perturb the correct protocol.** With all mutation flags FALSE, `PaxosFlagged.tla` must have the same reachable set *and* the same transition relation as pristine `Paxos.tla` at the bound. Nothing else in this design checks that adding the flag machinery left the one configuration everything rests on untouched.

Any mismatch fails CI. The TLA+ specs are the semantic source of truth. If the TypeScript model and TLC disagree, fix the TypeScript.

### 10.3 Layer 2 — the mutants are wrong in the way claimed

For each mutant, derive and record (do not hand-assert):

- whether it violates Agreement at its stated bound, and if so the shortest witness trace;
- the per-kind equivalence table from §5.5;
- whether it is adding, restricting, or neither, verified by checking `T_i ⊇ T_C` / `T_i ⊆ T_C` directly.

A mutant that breaks no safety property is a different pedagogical object from one that reaches disagreement, and the misconception text must say which. CI fails if a mutant's recorded classification changes without the YAML being updated.

### 10.4 Layer 3 — the bounded answer is the real answer

For every closure-property question (§6.4):

1. Bound-stability: the answer at bound `k` equals the answer at bound `k+1`. Unstable questions are dropped and the drop rate is reported.
2. **Independent oracle.** Derive "can `v` still be chosen?" a second way, from the safety argument rather than from the graph: once a quorum has promised at ballot `b` reporting maximum value `v`, no other value can be chosen at `b` or above. Implement this as a direct predicate on the state. Oracle and graph must agree on every shipped question.

The second check is what makes this layer worth anything. The oracle is a genuinely different derivation, not a second port of the same spec, so disagreement is informative in a way that TLC agreeing with the TypeScript is not.

TODO(Murat): confirm the oracle predicate before it is trusted — it encodes the core Paxos safety argument and deserves your eyes.

### 10.5 Layer 4 — the question is answerable by a human

A correct answer key is not enough; the learner must be able to reach it from what is on screen. Three mechanical checks:

1. **Justification exists.** Every shipped scenario carries a `Justification`. For an illegal step it names the first failing guard conjunct (free, given §5.1's ordered conjuncts) and splices the rule text from `content/paxos/rules.yaml`. For a legal step it names the conjuncts that were checked. Unjustifiable questions are dropped at generation time, not patched later.
2. **The justification references only visible facts.** The justification carries structured `refs` to state fields; the renderer declares which fields it displays. Assert `refs ⊆ displayed`. This is the sharp form of "the learner could have known this," and it catches renderer regressions that would otherwise make a correct question unanswerable.
3. **The renderer is injective on the bank.** Hash the rendered output of every scenario. Two scenarios with different `canonicalKey` that render identically make a question unanswerable regardless of the answer key. Collisions fail CI.

Plus human review: bank JSON diffs and `content/` changes go through PR review, and `pipeline/preview` renders a random sample of questions to static HTML for eyeballing.

### 10.6 Layer 5 — the bank actually diagnoses

This is the verification of the *game* rather than of the model, and nothing else in this document substitutes for it.

Implement synthetic learners and run them against each bank, over many seeds, with the real selection algorithm and the real Bayes scoring:

**Baselines — must score at or below chance:**
- `always-A`, `always-B`, `always-both`, `always-neither`, `uniform-random`
- `bigger-is-illegal` (picks the member with more messages / larger values)
- `prefer-first-shown`

If any baseline beats chance, the bank has a surface regularity and is broken. The enforced pair-type mix (§6.1) is what prevents the obvious ones; this harness is what proves it.

**Believers — must be identified:**
- `believer(i)` answers exactly according to mutant `i`, with noise ε.
- For each `i`, the run must end with `p_i > 0.9` and every `p_j (j ≠ i)` below 0.9, in at least 90% of seeds at ε = 0.1.
- Emit the full **confusion matrix** over all `i`, plus a `believer(∅)` run (a learner with no misconceptions, who must end with all `p_i < 0.1`).

The confusion matrix is the deliverable. Off-diagonal mass identifies misconception pairs the bank cannot separate — which is a *different* failure from model equivalence (§5.5) and is not caught by it: two mutants can be non-equivalent as models while the 20 questions you happened to sample never distinguish them. Any pair the matrix shows as inseparable is merged into a reported cluster (§7.2) rather than claimed individually.

### 10.7 What the first build actually measured

Recorded here because the numbers are the point, and because most of them contradict something this document originally assumed.

| Claim in the original spec | What measurement said |
|---|---|
| Mutants are adding or restricting | P5 and P6 are **overlapping** — effect edits both gain and lose states |
| D1 and D4 are distinct misconceptions | **Equivalent on every reachable state**; collapsed, per PICK §2.3 |
| Independent per-candidate Bayes throughout | Wrong for definitions; they are exclusive and need a categorical posterior |
| Contrasting pairs supply answer balance | Not on their own — the generator's enumeration order leaked into the key and "always answer A" scored 43% until sides were deterministically alternated |
| K=20 representatives per mutant suffices | Stratified sampling draws **zero** P2-separating states; a targeted scan is required |
| Trace questions test the learner's reading | They add no discriminating information at all (§6.5) — confirmed, they are presentation only |
| Learn and Test tracks | Test mode was wrong for a teaching tool; folded into one always-explaining mode (§7.1) |
| §10.5 covers "the question is answerable" | It covers *present*, not *legible*. The first build was unreadable and every check passed (§8) |

Bounds: 3 acceptors, 2 values, ballots `{0,1,2}`, BFS depth ≤ 14 → 74,439 reachable states, ~1.3 s. P2 first separates from Paxos at **depth 14** and not before. At two ballots it is exactly state-equivalent to Paxos (3,921 states each).

TLC agreed with the TypeScript BFS on all twelve configurations at two ballots, and on every agreement verdict.

Current identification rates: every targeted misconception 93–100%, off-diagonal ≤2% except P1/P2, no constant strategy above 37%, honest learners reported clean 97–100%.

**Expect the first run to look bad.** Twelve questions is 24 membership judgments, but each judgment only informs the configs that disagree on that scenario — typically one to three. That is thin evidence for eleven parameters under 10% noise. If the matrix is poor, the levers in order are: raise the `neither` share, raise `K`, split level 2 into two levels, and lower ε by making questions smaller. Report the matrix in the README and treat it as the app's headline quality number.

## 11. Tech stack and deployment

- **Language:** TypeScript (strict) everywhere. Node 20+.
- **Monorepo:** npm workspaces (or pnpm). Keep tooling minimal.
- **Web:** Vite + React. No UI framework beyond a small CSS file using CSS variables for theming. No router library; hash-based routing (`#/level/2`) is enough and works on Pages.
- **Tests:** vitest.
- **Lint/format:** ESLint + Prettier.
- **Bank loading:** one JSON file per level, fetched lazily. Keep each under 1 MB; if a bank is larger, cut `K`.
- **Persistence:** `localStorage` key `dyp:v1:progress`, wrapped in try/catch, with a reset button. Store the track choice, per-level answer history, and `p_i` inputs — never derived values, since §7.2 requires recomputation from scratch. Version the key so schema changes don't break old saves.
- **Deploy:** `.github/workflows/deploy.yml` on push to `main`. Build `packages/web` with Vite `base` set to `/<repo-name>/`, upload with `actions/upload-pages-artifact`, deploy with `actions/deploy-pages`. Enable Pages with source "GitHub Actions" in repo settings.
- **CI** (`ci.yml`, on PRs): lint → unit tests → regenerate banks and diff against committed → learner harness (§10.6) → TLC cross-check. The TLC job is slower; it can run on PRs touching `specs/`, `packages/models/`, or `packages/pipeline/`, and nightly. The learner harness is pure TypeScript and must run on every PR.

## 14. Notes for the implementing agent

- Correctness over features. A wrong answer key is worse than a missing level.
- Never generate questions or answers with an LLM at runtime, and never hand-write answer keys. Every answer comes from the build pipeline.
